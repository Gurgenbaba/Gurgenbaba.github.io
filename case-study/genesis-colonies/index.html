Die Aufgabe

Eine Welt, die nie pausiert.

In einem persistenten Strategiespiel gibt es keinen Speicherstand und keinen Neustart. Bauaufträge, Forschung und Flotten laufen nach Zeit ab, während viele Spieler gleichzeitig auf denselben Zustand zugreifen. Jede Aktion muss genau einmal wirken: Eine Flotte darf nicht doppelt ankommen, ein Gebäude nicht doppelt fertig werden, Ressourcen dürfen nicht aus dem Nichts entstehen.

Dazu kommt der Betrieb: Updates ohne Datenverlust, eine Datenbank, die mitwächst, und Werkzeuge, mit denen sich das Spiel im laufenden Betrieb steuern lässt.

Architektur

Der Server entscheidet.

Der Browser zeigt nur an. Jede Regel, jede Zahl und jeder Timer wird auf dem Server berechnet und in der Datenbank festgehalten.

Gelöste Probleme

Was unter der Oberfläche passiert.

  1. 01

    Datenbank-Umzug im Live-Betrieb

    Das Spiel startete auf SQLite und läuft heute produktiv auf PostgreSQL. Ein SQL-Übersetzer lässt denselben Code auf beiden Datenbanken laufen, eigene CI-Jobs prüfen Postgres-Transaktionen bei jedem Pull Request.

  2. 02

    Genau einmal, nie doppelt

    Eine zentrale Queue-Engine schließt fällige Bauaufträge, Forschung und Flotten ab. Jede Spieleraktion trägt eine Request-ID, damit ein doppelter Klick oder ein wiederholter Request nichts doppelt auslöst.

  3. 03

    Schnell trotz Hintergrundlast

    Globale Ticks liefen anfangs innerhalb normaler Seitenaufrufe und bremsten die Navigation. Heute erledigt ein eigener Worker-Prozess diese Arbeit, und Performance-Workflows in der CI schlagen Alarm, bevor es Spieler merken.

  4. 04

    Ein Account, mehrere Universen

    Spieler melden sich zentral auf dev.genesis-colonies.com an und wechseln von dort in isolierte Universen wie uni1.genesis-colonies.com. Jedes Universum besitzt seinen eigenen Spielstand und seine eigene Datenbank; die Übergabe läuft über kurzlebige, signierte Tokens. Alte Browser-Adressen bleiben als Redirect-Einstiege erhalten, während API-Routen bewusst stabil erreichbar bleiben.
